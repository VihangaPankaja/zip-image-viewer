Which download links can we grab?

Feasibility, not universal support.

Direct and linked files

Normal redirects, HTML links and supported landing pages are practical first steps. Review candidates, then use the existing guarded downloader. Bound every crawl by origin, depth, pages, bytes and time.

L01–L04 · D01–D03

Signed URLs and cookies

Playwright observes downloads and shares a browser-context cookie jar. A separate browser-assisted resolver is feasible. Some requests also need a method, body, CSRF token or live session. Start with controlled fixtures and supported sites.

L05–L06 · D05

The user's browser is separate

A remotely hosted Express server cannot read cookies from an existing personal browser. Offer explicit login in an isolated resolver or an opt-in local extension/helper. Do not scrape browser profiles or export all cookies.

Private per-user, per-origin sessions

Some downloads stay manual

DRM, CAPTCHA, device-bound sessions, one-time responses and access restrictions prevent universal support. Explain unsupported cases and retain manual import. A browser-only blob URL is not a reusable server link.

Scrubbing has two separate jobs

A thumbnail should respond as the pointer moves. Playback should resume quickly when the user releases it. Avoid starting an encoder for every pointer movement.

The current encoder runs from the beginning with four-second segments. startPrioritySegmentWindow delegates to the same full transcode; it does not prioritize a seek target. The EVENT playlist lists only generated segments, and the route waits up to 14 seconds for a missing file. These are code-based explanations to test, not measured root causes of every slow seek.

Preview cached thumbnail→Release at target time→Serve cached segment or prioritize window→Resume and fill ahead

Start with reliable segment publication and one complete low-resolution rendition for retained videos. That gives predictable random access once preparation finishes. Then add demand-driven windows for cold jumps on long videos. Each window needs compatible initialization data, timestamps, keyframes, audio boundaries and segment numbering. A new FFmpeg process with -ss alone is not enough.

Use the real emitted playlist and committed segment durations. Do not infer availability by counting files, especially once windows create gaps. Benchmark two- and four-second segments on representative hardware before choosing a default. Shorter segments trade request overhead and compression efficiency for finer seek and switch points. FFmpeg HLS options.

Adaptive bitrate, like the behavior you expect from YouTube

Keep hls.js in Auto mode and let its existing bandwidth and buffer logic choose the rendition. Auto already exists. The server must make the choices honest: the master route estimates bandwidth as height × 4,000, while the encoder uses a different ladder. The manifest also uses one hard-coded codec string. Those values should describe the actual outputs.

Start with an example ladder of 360p at 0.8 Mbps, 480p at 1.4, 720p at 2.8 and 1080p at 5.0 for video, plus audio and container overhead. These are current encoder settings to benchmark, not universal recommendations. Avoid upscaling. Tune for frame rate and difficult content. Keep 1440p and 2160p optional until CPU, storage and viewer demand justify them.

Warm a low rendition around the playhead and prepare higher ones within the worker budget. An advertised level that starts encoding from zero when selected can stall a viewer already halfway through. Preserve the player instance when switching Auto and manual levels. Show the actual active resolution and retain native Safari HLS support. hls.js level and automatic selection API.

Select now, fetch the rest later

Use a metadata review step before payload downloading. The picker needs a folder tree, file sizes, selection totals, Select all, Select none and a clear Start selected action. On the server, use WebTorrent's initial deselection option and file selection API. Validate file IDs against the resolved torrent.

Persist the info hash, metadata, selected file IDs and storage location. Reopen retained storage and verify pieces on restart. Track selected-file completion, not only the whole torrent's done event. Keep skipped files visible with a Download action. Adjacent files can share a piece, so some extra bytes are unavoidable. Availability still depends on peers. WebTorrent selection and storage API.

Retained torrents must survive session expiry and shutdown. Separate closing peer connections from deleting data. Give users distinct actions for Remove from list and Delete downloaded files. An archive inside a torrent still needs its own download and extraction path; selecting torrent files does not selectively fetch members inside a compressed archive.

Proposed performance checks

Targets to validate, not measured results or guarantees. Record device, CPU/GPU, codec, resolution, source readiness, network throughput and cache state. Use at least 30 jumps across each representative clip and report p50 and p95.

Scenario Initial target How to test
Cached thumbnail p95 under 100 ms Pointer movement to updated preview after storyboard load.
Prepared video seek p95 under 500 ms on LAN; under 1.5 s on a controlled 10 Mbps link Seek release to first displayed frame at the target. Seek outside the browser buffer into ready server segments.
Cold transcode seek First useful frame under 3 s on the benchmark machine Jump to 80% before that window exists. Report misses and encoder queue time. Revise the target if the hardware cannot keep up.
ABR under a bandwidth drop Downshift within two segment loads; under 1% rebuffer time over a 10-minute controlled run Drop 10 → 2 → 0.8 Mbps, recover, and log actual levels, buffer, stalls and dropped frames.

A sensible build order

Ship and measure each phase.
Phase 1

Fix daily friction

N01–N06, A01, A05, D01–D02. Compact themed controls, one timeline, truthful extraction progress, archive selection and durable HTTP recovery.

Phase 2

Finish file workflows

A02–A04, A06–A08, F01–F04, F06. Add archive recovery, nested browsing, export, local import, bounded text and complete audio.

Phase 3

Discover and batch

D03–D06, L01–L04. Bounded crawling, filtered bulk selection and fair scheduling. Prototype L05; require L06 before persisted credentials or shared deployment.

Phase 4

Consolidate tooling

B01–B04 can proceed after a baseline without waiting for every feature. Pin stable compatible releases, prove lint parity, add CSS lint and retain checks. Then move colocated tests into dedicated suites with mirrored app paths in B06.

Phase 5

Prepare and review

P01–P02, F05, N07–N08, B05. Prefer saved renditions, add global search and finish the device audit with deliberate storage limits.

Stack decisions

Keep / change Reason Verification
Keep React + Express + typed contracts Archives and downloads fit existing feature boundaries. No server-rendering rewrite is needed. Extend oRPC/Zod contracts and real integration fixtures.
Migrate to Vite+ Consolidate compatible dev/build/test/lint/format commands using stable compatible releases. Preserve server/shared output, container imports, coverage and all browsers.
Oxlint/Oxfmt with rule parity Use supported rules and retain narrow ESLint checks for useful gaps. Formatting has one owner. Document strict typed rules and exceptions; test deliberately invalid fixtures.
Add Stylelint Validate CSS and prevent theme-token regressions. Fix the baseline; compare all device/theme screenshots.
Extend SQLite and local workers Retain HTTP jobs, archive manifests and metadata without a distributed queue. Restart, ownership, quota, interruption and deletion checks.
Optional isolated browser resolver Use for supported dynamic/authenticated downloads that HTTP cannot resolve. Explicit login, session isolation, network sandbox and redacted diagnostics.
Keep hls.js, FFmpeg and WebTorrent Completed work covers playback, caching and selective torrents. Reuse limits and preparation; replace only for measured incompatibilities.
